我维护开源库的时间足够长，长到能看清哪些设计决定能经受住现实的考验。这个规律简单得让人不太舒服：API 最小的那些库还活着，聪明的那些都归档了。

## 表面积是一种负债

每一个导出的函数都是一个承诺。不是关于行为的承诺 —— 而是关于你*未来的注意力*的承诺。每个函数都需要保持准确的文档、保持有用的报错信息，以及一个不能随便改、一改就得引发讨论的签名。

```ts
// tiny-query：全部的 API
const db = createDb({ url: process.env.DATABASE_URL });
const rows = await db.query('select * from posts where tag = $1', [tag]);
```

两个函数。这就是库的全部。当有人给它提 issue 时，我能把整个设计装在脑子里作答。这不是一个无关紧要的奢侈 —— 这是我至今还愿意回复的原因。

## 聪明的 API 为什么会死

我在架构上最引以为傲的那些库，恰恰是我亲手废弃的。它们有 builder、插件、生命周期钩子、一套哲学。而每一个的死法都一样：

1. 用户撞上一个抽象覆盖不到的边界情况。
2. 他们提了 issue。诚实的回答是「这个抽象不适合你的场景」。
3. 我加一个逃生舱。逃生舱之间会互相吸引。
4. 两年后，这个库有三十个逃生舱，再也没有形状。

抽象不是因为那个边界情况而错的。它错在：每一个抽象迟早都会遇到自己的边界情况，而这场相遇的成本全部由维护者支付。

## 无聊的替代方案

替代方案不是不做抽象。而是把抽象提前一层停下 —— 停到不够优雅的程度。返回普通的行数据而不是实体对象。接收 SQL 字符串而不是查询构造器。接受一个普通配置对象而不是带中间件的工厂。

这些决定在做出的当天都会有点难为情，因为普通的东西不如聪明的东西亮眼。但难为情很便宜，维护很贵。

## 我现在真正优化的东西

设计 API 时我只问一个问题：*这个签名我能守一辈子吗？* 不是「它今天好不好」，而是「当我早已忘记自己为什么这么写、在一个几乎不碰的仓库里，我还能不能没有愧疚地对外加功能说不？」

小 API 让「不」变得容易。这才是它真正的功能。小表面积不是为了极简而极简；它是一道边界，保护着开源里唯一稀缺的资源 —— 维护者继续下去的意愿。
